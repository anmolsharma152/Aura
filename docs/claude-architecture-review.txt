Architecture Review
The core pattern (lean C PAM client → Unix socket → Python daemon) is exactly right. Most failed implementations do ML inference inside PAM space; you've correctly avoided that. A few issues:
Critical bug in PAM config:
In your README, gdm-password has:
iniauth        revert        pam_aura.so
revert is not a valid PAM control flag. This will cause GDM to fail to parse the stack entirely. It should be sufficient, same as sudo.
Security hole in the socket:
pythonos.chmod(SOCKET_PATH, 0o666)  # Ensure accessibility across services
This lets any process on the system connect and request auth decisions. GDM runs as root, sudo runs as root — they don't need world-readable. Use 0o660 and add aurad to a dedicated group (aura), then add gdm and the PAM-calling services to that group.
Blocking single-threaded daemon (connects to your Q2):
Your run() loop is sequential. If a sudo call is mid-verification (camera warmup + inference = 300ms–1.5s on your i5), a second PAM invocation — say, a polkit prompt — hits the socket and your C client's 1.5s SO_RCVTIMEO expires before the first request even finishes. The fallback to password works, but it's a UX failure and may confuse users.
Camera open/close per call:
pythondef verify_identity(self, username):
    self.init_hardware()          # Opens /dev/video0
    ret, frame = self.camera_device.read()
    self.camera_device.release()  # Immediately closes
V4L2 cameras need several frames to settle auto-exposure and white balance. The first frame off a cold-open is garbage. You'll get bad embeddings. Either keep the capture object warm in daemon memory, or discard the first 3–5 frames after open.

Q1: Dumping Windows Hello USB Traffic (Wireshark + USBPcap)
This is the right approach to recover the Realtek activation sequence. Here's the exact method:
On Windows (capture side):

Install USBPcap alongside Wireshark. During install, it adds kernel filter drivers per USB root hub.
Open Wireshark, select the USBPcap interface that enumerates your camera's hub (check Device Manager → Universal Serial Bus controllers to find which root hub 0bda:58c2 is on).
Set this display filter before triggering Hello:

   usb.transfer_type == 2 && usb.endpoint_number == 0
This isolates URB_CONTROL packets on the default control pipe — exactly where UVC SET_CUR/GET_CUR extension unit commands live.
4. Lock screen, authenticate with Windows Hello, stop capture immediately after.
What to look for:
The activation sequence will appear as URB_CONTROL out packets where:

bmRequestType = 0x21 (Class request, Host-to-Device, Interface recipient)
bRequest = 0x01 (SET_CUR)
wIndex upper byte = Extension Unit ID (Unit 7 in your dmesg)
wIndex lower byte = the interface number
wValue upper byte = the Control Selector (CS) — this is the key byte

The payload data following that header is the vendor-specific command that toggles the IR emitter. You're looking for 1–4 packets in sequence right after the face detection event starts.
Alternatively on Linux (if you can dual-boot briefly):
bashsudo modprobe usbmon
# Find your camera's bus number from lsusb output
sudo cat /sys/kernel/debug/usb/usbmon/1u | grep -A2 "0bda"
# Or use tshark directly on the usbmonX interface
sudo tshark -i usbmon1 -Y "usb.transfer_type==2" -w hello_capture.pcap
Then replay Windows Hello and parse the pcap. tshark -r hello_capture.pcap -T fields -e usb.capdata extracts the raw payload bytes.

Q2: ONNX Single-Threaded Daemon Edge Cases
The real risks in your current architecture:
1. Concurrent auth timeout race (the main one)
As noted above — second PAM call during active verification will hit the 1.5s SO_RCVTIMEO and fall through to password. Fix with a thread-per-connection model:
pythonimport threading

def run(self):
    # ... socket setup ...
    while True:
        conn, _ = server.accept()
        t = threading.Thread(target=self._handle_conn, args=(conn,), daemon=True)
        t.start()

def _handle_conn(self, conn):
    data = conn.recv(1024)
    if data:
        username = data.decode('utf-8')
        result = self.verify_identity(username)
        conn.sendall(result)
    conn.close()
But then add a threading.Semaphore(1) inside verify_identity to serialize camera + inference access — cv2.VideoCapture is not thread-safe.
2. ONNX session initialization latency
Your __init__ loads the ONNX session synchronously. If systemd starts aurad and PAM immediately calls in (e.g., during GDM startup), the session may not be ready. Add a readiness signal — write a PID file or touch a /run/aura.ready file only after self.ort_session is fully initialized.
3. Your 15MB idle RAM target is likely unachievable
ONNX Runtime's base footprint is ~30–40MB resident just from the shared library. MobileFaceNet quantized adds ~4MB, MiniFASNet another ~2MB. Budget closer to 50–60MB idle. Worth benchmarking with smem -P aurad before committing that metric to any presentation.
4. cv2.dnn.blobFromImage normalization mismatch
Your current preprocessing:
pythonblob = cv2.dnn.blobFromImage(face_frame, 1.0/127.5, (112, 112), (127.5, 127.5, 127.5), swapRB=True)
This is correct for MobileFaceNet's expected [-1, 1] input range. But blobFromImage outputs NCHW float32 — verify that your specific ONNX export also expects NCHW. Some MobileFaceNet exports expect NHWC. Check with self.ort_session.get_inputs()[0].shape.

Bug 1 (Critical): Protocol Deadlock
C client — pam_aura.c:79:
cwrite(sock, username, strlen(username));  // sends "anmol", no terminator
Python daemon — aurad.py:199:
pythonwhile True:
    chunk = conn.recv(1024)
    if not chunk:
        break
    data += chunk
    if b"\n" in data or b"\x00" in data:  # waits for terminator that never comes
        break
What happens: C writes anmol and then blocks on read() waiting for a response. Python reads anmol, finds no \n or \x00, loops back to recv() and blocks waiting for more data. Both sides are waiting on each other. C's SO_RCVTIMEO fires after 2 seconds, it closes the socket and returns PAM_AUTH_ERR. Python eventually gets EOF, processes the username, sends the auth result — into a closed socket. Every single auth attempt fails silently.
Fix — one line in the C client:
c// Replace the write line with:
char msg[MAX_USERNAME_LEN + 2];
snprintf(msg, sizeof(msg), "%s\n", username);
write(sock, msg, strlen(msg));

Bug 2 (Critical): Timeout Mismatch
c// pam_aura.c
#define SOCKET_TIMEOUT_SEC 2
python# aurad.py
max_duration = 5.0  # daemon tries for 5 seconds
Even after fixing the deadlock, C gives up after 2 seconds. The daemon may need up to 5 seconds if lighting is poor or the user needs a moment to position their face. Every slow-but-valid auth will fail from the C side.
Fix:

handle_client spawns a thread per connection. Two sudo prompts in quick succession means two threads both calling verify_user simultaneously, both hitting self.camera.read_frame() and self.inference.face_session.run(). cv2.VideoCapture is not thread-safe. Fix — add to AuraDaemon.__init__:

    if not self._verify_lock.acquire(timeout=8.0):

        return False
    try:
        # existing logic
        ...

        self._verify_lock.release()
This serializes camera access but still handles concurrent requests gracefully (second request queues and waits rather than crashing).
